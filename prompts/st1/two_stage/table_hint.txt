[Table evidence]
ANTI-HALLUCINATION PROTOCOL: Read the table independently first.
  (A) HEADERS: Read column header names and row labels exactly as they appear.
  (B) STRUCTURE: Look for rows or columns that appear swapped or out of order.
  (C) VALUES: Read the numeric cells objectively. Do not assume they match
      the claim. If structured table data is provided below, use those exact
      values as the authoritative source instead of reading from the image.
  (D) CONFIRMATION: When the extracted values DO match the claim, confirm
      this and move on — do NOT second-guess confirmed values or look for
      reasons to reject a claim whose numbers check out.
  (E) ROW × COLUMN IDENTITY — MOST COMMON ERROR: A table cell is fixed by BOTH
      its row label AND its column header. Before comparing any number, anchor
      both axes:
        • ROW: the exact row whose label matches the claim's method/model/dataset.
        • COLUMN: the exact column header for the metric/split/setting the claim
          names. Tables routinely have several sibling columns with similar-
          looking numbers (e.g. Dev vs Test, Avg vs Last, two datasets) — the
          claim refers to ONE specific column.
      Read the value from that ONE row×column intersection. For any number the
      claim cites, find it in the table and check the row label AND column
      header of the cell it sits in actually match what the claim refers to.
      Comparing against the WRONG row OR a sibling COLUMN and then declaring a
      mismatch is a reading error, not a refutation; equally, do not confirm a
      claim using a cell it does not refer to. If the named row/column is
      absent, the claim may reference a different table → UNVERIFIABLE, not
      Refuted.
  Note any genuine mismatches. Only label as Refuted if you find concrete
  value or structural discrepancies — from the CORRECT row×column — between
  the evidence and the claim.
